# Сценарий защиты (8–10 минут) и демо

**Формат:** 3 минуты слайдов → 5 минут живого демо → 1–2 минуты итогов → вопросы.
**Подготовка за 10 минут до выхода:**

```bash
docker compose down -v && docker compose up -d --build   # чистые демо-данные
python scripts/e2e_smoke.py                               # стенд работает (потом снова down -v / up, чтобы очистить)
```

Откройте вкладки: `localhost:8080` (клиент, пекарня), второе окно в режиме инкогнито для банка (`analyst@bank.ru`), `localhost:8000/api/docs`, терминал с командой chaos. Масштаб браузера — 110%.

---

## Часть 1. Слайды (3 мин)

**Слайд 1 — Титул (10 с).** «CreditFlow — кредитный кабинет, где предприниматель видит путь от задачи до денег, а банк управляет этим путём в одном продукте».

**Слайд 2 — Проблема (40 с).**
«У Марии пекарня, нужна вторая печь. Сегодня она: 1) не знает, какой продукт брать; 2) заново вводит то, что банк может узнать по ИНН; 3) после отправки попадает в чёрный ящик; 4) получает "нет" без объяснений, хотя банк мог дать 2 млн вместо 3. На стороне банка аналитик собирает данные из пяти систем, а руководитель не видит воронку».

**Слайд 3 — Решение (40 с).** Три принципа:
1. **Ноль лишнего ввода**: ИНН → ЕГРЮЛ, ФНС, БКИ.
2. **Прозрачность**: каждый этап виден клиенту в реальном времени, каждое решение объяснено.
3. **Не "нет", а "вот как можно"**: встречные предложения из той же модели.

**Слайд 4 — Как устроено решение (40 с).** «Скоринг ≠ решение — как и сказано в кейсе. Сначала стоп-факторы политики, затем балльная карта риска заёмщика, не зависящая от суммы, затем кредитная логика: лимит по денежному потоку с DSCR ≥ 1,3 и подбор альтернатив. Сложные случаи уходят человеку с готовой рекомендацией».

**Слайд 5 — Архитектура (30 с).** «Конечный автомат статусов, транзакционный outbox в PostgreSQL, горизонтально масштабируемые воркеры, мягкая деградация при сбое источников, аудит каждого действия, принцип четырёх глаз. Всё поднимается одной командой `docker compose up`».

| 0:30 | «💬 Помощник» → «Нужно 3 млн на новое оборудование на 2 года» | «Пишем своими словами. Ассистент разобрал цель, сумму и срок и подобрал продукты. Первым идёт льготный: отрасль Марии приоритетная, а она об этом не знала» |
| 1:00 | «Оформить» → шаги «Компания», «Финансы» | «Компания из ЕГРЮЛ, выручка и расходы из ФНС. Мария только подтверждает. Черновик сохраняется: можно уйти и вернуться» |
| 1:40 | Согласия → «Отправить» | «Смотрите: этапы идут в реальном времени. Это реальный асинхронный конвейер: воркер запрашивает ЕГРЮЛ, ФНС, БКИ, антифрод» |
| 2:10 | «Одобрена» → «Что повлияло» → «Принять» | «Решение за секунды. Мария видит, почему ей одобрили. Принимаем — договор сформирован» |
| 2:30 | 🔔 → код → «Подписать» | «Код подписи приходит в кабинет — без SMS, как требует кейс. Подписали — деньги на счёте, график платежей» |
| 3:00 | Окно банка → дашборд | «Банк видит воронку, долю автоматических решений и время до решения» |

| 4:00 | «Одобрить» 25 млн → «На согласовании» | «Больше 15 млн — принцип четырёх глаз: решение уходит риск-менеджеру» |

| 4:50 | *(Если есть время)* терминал: chaos для БКИ → новая заявка | «БКИ упало — заявка не потерялась, а ушла специалисту с пометкой. Это и есть отказоустойчивость» |

**Запасной план:** если сеть или Docker подведут — записанный скринкаст 3 мин (запишите заранее по этому сценарию) и скриншоты в приложении к презентации.

## Часть 3. Итоги (1 мин)

**Слайд 6 — Что готово.** «Работающий сквозной прототип: 5 продуктов, 16 статусов, 4 роли, 5 смоделированных внешних систем; 24 автотеста и e2e-скрипт; OpenAPI, Postman, диаграммы; запуск одной командой».

**Слайд 7 — Эффект и развитие.** «Для клиента — заявка за 5 минут без повторного ввода и альтернатива вместо отказа. Для банка — автоматические решения по типовым заявкам и аналитик, который тратит время только на сложные. Дальше: модель на исторических данных, транзакционные признаки, BPMN-движок и интеграции через корпоративную шину. Архитектура для этого уже готова».
